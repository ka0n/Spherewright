# Safety model

The explicitly authorized native migration exceptions are exactly `0.10.34.28529 → 0.10.35.29057`, `0.10.34.28529 → 0.10.35.29088`, and `0.10.35.29088 → 0.10.35.29104`, only within expired-primary reauthorization. The last pair may follow the already durable first `28529 → 29088` transition in the same Journal; no other direct or chained jump is authorized. Here “version match” below means ticket, primary and Journal effective **source** version agree and the host is the researched target; every other cross-version pair rejects. Historical Journal `GameVersion` and earlier transitions stay unchanged, and only the new transition is durably appended after adoption. The read-only Journal lease is released only for this write while the primary lease and pending checkpoint still block saving/gameplay; persistence failure rejects adoption. Normal save then reads back the exact owned identity, native format tuple, current version and tick before signing a target-version credential. Unknown/mixed save-format tuples, downgrade, replay and default cross-version resume remain forbidden.

Expired healthy planned-restart provenance may only enter the explicit `reauthorize_expired_primary` prepare/commit flow. It is never an active resume capability: the exact ticket-bound primary must match its saved tick, complete embedded identity, current version and peaceful mode; both protected ticket replicas and the original Journal must agree. Prepare binds complete file/Journal evidence and menu revision to a short plan, discloses its scope, and requires subsequent conversation consent plus a plan-specific digest echo. Commit revalidates all evidence, holds the primary and Journal read-only through adoption, and writes protected attempt evidence plus a durable consumed tombstone before loading. No expiry edits, LastExit fallback, arbitrary names, copied world or fabricated history are allowed. A crash/failure after consumption is fenced for manual reconciliation, not automatically retried. Only normal saving after successful identity and Journal adoption issues a fresh ticket. This implementation does not claim live validation merely from unit tests.

- `AllowWrites` defaults to `false`; every mutation uses fresh prepare, an idempotent commit, terminal observation, and relevant readback. `AllowUnownedRichReads` and `AllowUnownedNormalWrites` also default to `false` and are independent.
- `OwnedBySpherewright` means protected Spherewright save/provenance ownership. It is not normal-action authority. A manually loaded world stays unowned unless it passes the separate import/adoption workflow. `IsCurrentExactUnownedSession` identifies only the exact loaded `GameData` and current session with no protected adoption in progress.
- Public rich reads of that exact unowned session require `AllowUnownedRichReads=true`. `ReadAccessMode` reports `restricted` or `observed_unowned` independently of write authority; `WritesAllowed` may be true in either mode when normal actions are authorized. Public read capabilities still hide player, factory, progression, recipe, resource, and Overseer data when rich reads are off. The internal action reader does not broaden those public capabilities.
- Normal-action authority for the exact unowned session requires both `AllowWrites=true` and `AllowUnownedNormalWrites=true`. It adds `action.read` and `normal-game.prepare` capability without changing `OwnedBySpherewright=false`. It does not require `AllowUnownedRichReads`, `AllowUserSaveImport`, Peaceful mode, Passive mode, or a particular Dark Fog aggressiveness. Unowned observation remains read-only whenever `AllowUnownedNormalWrites=false`.
- The ordinary Save action on an authorized unowned session saves the currently loaded native save identity in place. It neither renames nor clones the save, performs import/adoption, nor creates owned save provenance or a resume ticket. Owned Save remains on its existing protected path.
- Authorized unowned interplanetary flight uses the normal flight safety and state lifecycle without a Spherewright FlightCheckpoint. A successful flight does not seal or retire a nonexistent checkpoint; ordinary failure does not require checkpoint recovery. Owned flight retains its protected checkpoint lifecycle.
- Finite unowned blueprint progress is in-memory and bound to the generated current `SessionId`. Cancel works only for that same session; replacing the world/session or restarting Plugin/DSP discards this progress. Owned blueprint progress keeps its existing durable save-bound behavior. Public blueprint inspection/export remains on its separate owned-world policy.
- Protected Save Import, Owned Resume, and FlightCheckpoint reload remain separate identity/provenance workflows. Normal unowned actions do not arm or consume their authority.
- Rich observed reads still require the exact current `sessionId`, current `GameData`, a ready current world, and the matching current local planet where required. Wrong, stale, replaced, or mismatched requests remain rejected.
- New worlds are peaceful, 1x resources, sandbox-disabled, and created through DSP's new-game path. Unrelated saves are never enumerated or actively loaded. A player-loaded current world gains ownership only through the separate exact-session Save Import prepare, a subsequent conversation confirmation, and a normally saved new owned copy; ordinary unowned writes never adopt the world.
- `combatModeStatus` and `sandboxModeStatus` remain explicit runtime evidence. Non-peaceful mode retains the existing owned-write and protected-import policy. Sandbox state and resource multiplier do not gate normal actions and never expand the bounded action surface. Dark Fog aggressiveness is telemetry only.
- Computer Use, screenshots-as-state, visual recognition, and keyboard/mouse macros are forbidden for gameplay execution and acceptance.
- No action may grant items, inject storage/buffers/energy, write technology progress, directly complete prebuilds, teleport the player, change game speed, or edit a save. Normal Save may write only the exact current native save identity in an authorized session, the separate owned identity, an internally generated protected checkpoint, or the new copy explicitly authorized by Save Import. It does not enumerate, arbitrarily open, rename, or delete saves.
- Refuelling must move already-owned native fuel and prove count plus proliferator-point conservation. Research-result acknowledgement uses the native UI fade/close lifecycle and never changes research state directly; it is suppressed during `observed_unowned` reads so observation does not mutate the UI.
- Logistics-station fleet transfer may move only already-owned item `5001`/`5002` between the player package and the matching idle fleet counter. It binds idle and working craft plus prefab capacity, rejects proliferated deposits and collectors, and must preserve cargo slots, energy, warpers, configuration, the other fleet, working craft, the player hand, and unrelated package items. It never creates a drone/vessel or writes station cargo.
- Normal actions must prove the same costs the game imposes: range, inventory, capacity, energy, recipe/technology unlock, construction, power, and elapsed game ticks.
- A move or harvest that continuously has no core energy, reactor energy, current reactor item, or usable fuel for 600 game ticks is terminated as a proven `action_failed`; Spherewright aborts only its exact owned player order and never injects recovery energy or fuel.
- A powered move is also terminated as `action_failed` when it accumulates less than 0.75 metres of physical displacement for 180 game ticks, or when 600 game ticks of continued motion fail to reduce the best remaining target distance by at least 1 metre. These checks stop the exact owned order before the global timeout; they do not classify a fully power-starved grace window as a collision.
- `prepare_move` validates a fresh finite surface target but does not claim path-collision prediction. A stall result explicitly says not to retry the same target and gives bounded 5 m single-obstacle / four-by-4 m orthogonal recovery guidance. Every candidate remains a separate audited prepare/commit Move; the Plugin performs no unbounded automatic search, teleport, direct position write, or injected input.
- DSP exposes one current player order. Move and harvest actions therefore use single-flight at commit time: while either is non-terminal, a second player-order commit returns retryable `SERVER_BUSY` instead of replacing the first order and leaving two misleading action records.
- All current DSP/Unity reads and writes are dispatched to Unity's main thread. Pipe workers see only immutable DTOs.
- Plans bind the bridge/session/planet, action type, exact target identity, parameters, before-state hash, and resource budget.
- The 0.4 scope permits bounded native blueprint construction and per-entity native upgrades, not unconstrained multi-object writes. Blueprint inspection/export remains restricted to explicit code or selected current-owned entities, with bounded decompression/object counts and explicit unsupported-content rejection; metadata is untrusted. Finite BlueprintBuild and Cancel use ordinary materials, native prebuilds/drones, bounded per-object execution, and explicit partial outcomes. Owned progress remains durable and save-bound. Unowned progress is session-only in memory; it cannot be recovered or adopted after session/process replacement. Cancellation stops unsubmitted objects and does not remove completed objects.
- The executable upgrade subset is ordinary manufacturing assemblers plus basic sorter2011→2012 only. It calls native `DoUpgradeObject`, never writes `protoId`, consumes a complete higher-tier item and refunds the old item into reserved package space. It binds revision and fresh identity/configuration/filter, checks live cargo, reciprocal links and native timing/power immediately, and quarantines any uncertain cost/result instead of replaying. A sorter needs both actual factory links matching its pick/insert targets, not merely a valid subset of existing edges or positive cached target IDs. Assemblers reset processing progress; basic sorters rescale the retained cycle fraction. Belts, advanced stacking sorters and other upgrade families are not enabled.
- Finite blueprint execution exposes partial per-object outcomes, preserves normal materials/drones/time, and caps per-frame work. Cancellation stops unexecuted work only. Owned restart recovery requires durable owned-bound evidence reconciliation and fresh tokens. Unowned progress is intentionally discarded on process/session replacement, and a partially completed module must never be replayed or described as rolled back.
- Save-import prepare binds the exact unowned process/session/revision/`GameData` without reading or exposing world content. Its plan remains non-committable until a later user message explicitly confirms the returned disclosure; commit requires the caller to declare that confirmation and both original-save/journal boundaries, then revalidates peaceful mode, records the actual sandbox/resource settings, and requires local-factory readiness before its sole normal-save attempt. Sandbox and resource multiplier do not gate import. A true save return without exact header proof quarantines import for that loaded session; only result lookup is allowed until the player intentionally reloads the original into a new session.
- Factory observations expose a complete mutable `stateHash` and a stable `endpointStateHash`. Logistics builds bind the latter so identity, pose, and existing connections remain exact while ordinary production progress and buffers may advance; belt input/output slots are treated as explicit physical endpoints when extending a path.
- The v0.4 diagnostic bundle is composed only from deep-copied public Overseer DTOs captured in one Unity-main-thread work item. It rejects any cross-domain factory/tick mismatch, uses a versioned public allowlist schema, and has no field for save identity, filesystem paths, auth credentials, or action plan credentials.
- Before creating a sorter prebuild, completion attribution snapshots older same-item entities at the prepared source pose. Those IDs cannot satisfy the new action's readback, because DSP legitimately anchors multiple sorters at an identical building-side position.
- Commit results are cached by `(sessionId, idempotencyKey)` across Pipe reconnects. Each session has its own configured capacity, entries expire after `IdempotencyRetentionMinutes`, same-key retries replay during that window, and different requests conflict.
- If a mutation starts but the result cannot be proved as before or expected-after, the session write subsystem is quarantined. For an authorized unowned session, quarantine remains in memory and requires the same exact running session; it creates no resume ticket, save provenance, or restart recovery. The available in-process quarantine reconciliation is limited to its supported outcome-unknown Build proof. An uncertain unowned Save or other action without a supported proof stays quarantined; it cannot switch into owned recovery.
- Owned-game quarantine can be cleared in-process only by the documented proof for the exact retained outcome-unknown Build; reconciliation never repeats that mutation. Protected resume continues to bind the exact owned identity, source shutdown, minimum tick, planet, peaceful state, and the per-save Journal checkpoint. Newly issued tickets record Journal identity, tracking boundary, and minimum durable sequence. Resume validates that protected file before load and after adoption; a missing, recreated, truncated, or identity-mismatched Journal leaves the loaded world restricted, preserves the ticket for repair/retry, and blocks automatic save and gameplay writes. Legacy tickets without this extension remain load-compatible and are upgraded by the next healthy owned save. Sandbox/resource settings are preserved and reported but do not gate adoption.
- Explicit newer-LastExit recovery is a separate opt-in to the existing protected resume, not a forged quarantine or automatic fallback. It requires actual conversation confirmation, a valid healthy Journal-bearing ticket, exact approved candidate tick and known progress floor, bounded embedded identity/version/peaceful validation and unchanged full-file evidence. Commit holds a read-only file lease through adoption; older/drifting/unsupported sources reject. Candidate tick must survive adoption, Journal confirmation and normal primary resave. No arbitrary path, directory scan, autosave selection or offline primary overwrite is allowed.
- Owned flight checkpoints are persisted and header-verified before native launch. Reload requires the protected token and a persisted recovery-required/interrupted-flight lifecycle, cannot accept a save name, and adopts the payload only after the internal slot, exact tick, embedded primary owned identity, origin planet, and peaceful state match. Sandbox/resource settings are preserved and reported but do not gate adoption. Failure may repeat this same load; success removes the capability immediately, a covering primary save retires the ticket, a newer exact primary header supersedes legacy state, and every ticket has a 24-hour expiry. Authorized unowned flight never creates or exposes this protected recovery capability.
- The Pipe authentication token, absolute private paths, raw save identity/content, private game objects, and stack traces are never returned through MCP or written to normal logs. Opaque plan, one-time resume, and reusable checkpoint tokens are returned only in their intended authenticated DTO fields and are excluded from ordinary logs and committed evidence.
- The Named Pipe uses a per-process random name, startup-rotated token, and ACL restricted to the current Windows SID.
- The old sandbox basic-line experiment is excluded from M0 Plugin compilation and the public write surface.

Material inventory cuts use the same public rich-read policy as factory inspection: owned worlds are readable, and an exact current unowned session is readable only with `Safety.AllowUnownedRichReads=true` (`ReadAccessMode=observed_unowned`). `Safety.AllowUnownedNormalWrites` alone does not enable the public query. This observation grants neither ownership nor write authority; the private action reader remains separate.
